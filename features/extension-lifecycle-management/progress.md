# Extension Lifecycle and Reconnection Management — Progress

## Goal

Implement safe extension health reporting, pause/resume, revocation, soft
removal, and explicit recovery after reinstall while preserving the durable
Facebook connection and its Groups, jobs, names, and history.

## Source Documents

- `features/extension-lifecycle-management/feature.md`
- `features/multi-account-facebook-publishing/FEATURE.md`
- `features/extension-owned-maintenance-sync/feature.md`

Implementation must preserve the existing rule that
`facebookConnectionId` is the durable owner of Groups and Publishing Jobs.

### Review Notes

```text
Status: COMPLETE
Review date: 2026-10-08

Current architecture:

- `extensionInstanceId` is generated by the extension and stored in
  `chrome.storage.local`.
- Removing the extension may remove that local state, so loading it again
  creates a new installation identity.
- `ExtensionInstallation` is linked to `FacebookConnection`.
- Groups and Publishing Jobs use `facebookConnectionId` as durable ownership.
- Registration and heartbeat currently use upsert behavior.
- Existing registration and heartbeat paths set installation status back to
  `ACTIVE`; therefore deleting a database row or adding a status alone would
  not safely revoke an extension.
- Dashboard connectivity is derived from activity timestamps with a two-minute
  offline threshold.
- Worker status already distinguishes publishing and Facebook interruption
  conditions such as BLOCKED, LOGIN_REQUIRED, and ACCOUNT_MISMATCH.
- No pause, resume, revoke, archive, restore, or reconnect management endpoints
  exist yet.
- Worker requests currently rely on the Clerk user ID and extension instance
  ID headers; no revocable per-installation credential exists.
- The current working tree includes immediate authenticated registration,
  clearer popup connection stages, short dashboard setup polling, and backend
  extension-name uniqueness.

Primary risks:

- Hard-deleting a connection allows a live extension to recreate it through
  register/heartbeat upsert behavior.
- A revoked record can currently be reactivated by ordinary traffic.
- Administrative pause/revoke is not separated from Facebook health.
- A reinstall appears as an unrelated new connection and has no explicit
  recovery workflow.
- Rebinding by matching Facebook ID automatically would be ambiguous and could
  let two installations contend for one connection.
```

  version counter (`credentialHash`, `credentialVersion`).
- The extension stores the plaintext only in `chrome.storage.local`
  (`extensionCredential`), which page scripts cannot read, and sends it as the
  `x-extension-credential` header on every API call when present.
- Worker endpoints authenticate with instance ID plus credential
  (`verifyWorkerIdentity`). REVOKED is checked before the credential.
  Plaintext credential values never leave issuance, are absent from API
  responses (hashed fields stripped in `sanitizeConnection`/
  `sanitizeInstallation`), and are never logged.
- `register` returns an explicit `RegistrationOutcome`. Known PAUSED stays
  paused, REVOKE_PENDING stays pending (or finalizes to REVOKED once leases
  expire), and a REVOKED tombstone returns outcome `REVOKED` with a reason and
  is never mutated or reactivated.
- Heartbeat refreshes liveness but never changes the lifecycle, and preserves
  persistent worker statuses (PUBLISHING, BLOCKED, LOGIN_REQUIRED,
  ACCOUNT_MISMATCH, CHECKPOINT_OR_VERIFICATION, CAPTCHA_OR_CHALLENGE,
  MANUAL_INTERVENTION_REQUIRED).

  register issues a credential and bumps `credentialVersion`; after that,
  missing, wrong, or revoked credentials fail closed with 403.
- Revoked installation tombstones are retained; no hard deletes.
- `maybeFinalizeRevocation` now returns `Promise<boolean>` and `register`
  branches on the result, so a finalized REVOKE_PENDING cannot fall through to
